# 更新应用与发布版本

## 用户：检查并升级

设置页“版本与更新”提供“发布页”和“检查更新”。检查只在点击后向 GitHub 查询本仓库最新正式发布；没有正式发布时显示相应提示，网络失败会显示错误。应用不静默下载、替换或执行程序。

1. 查看发布说明，确认系统要求、已知问题和验证范围。
2. 下载该版本的 `StateLite-vVERSION-macos-arm64.zip` 和 `SHA256SUMS`，放在同一目录执行 `shasum -a 256 -c SHA256SUMS`。
3. 在旧应用中将风扇切回系统，等待恢复确认，再退出应用。不要在自定义会话运行时直接替换程序。
4. 解压新版本，替换固定位置的完整 `.app`；不要只替换 `Contents/MacOS` 中的单个文件。
5. 打开新版本，检查监控读数。首次再使用自定义风扇时，代码身份改变会要求授权更新专用助手。

菜单栏指标、排列方式、模块布局和已保存目标偏好保留在系统偏好中，普通应用替换不会清除它们。保存的目标只是下一次编辑的初始值，**不会在启动时自动接管风扇**。

同一版本号也可能对应不同源码构建。助手绑定实际代码身份，不只比较版本字符串；自行重新构建或换回旧构建也可能再次要求管理员授权。不要承诺“版本号没变就绝不弹密码”。

## 维护者：main 的日常更新

```sh
git switch main
git pull --ff-only
./test.sh
./build.sh
codesign --verify --deep --strict StateLite.app
```

提交应包含相关源码、必要测试和文档。`main` 的 CI 运行构建及无硬件测试；它不安装 root 助手、不弹授权、不调用 `--fan-verify`，不能证明实际调速或恢复。

`main` 更新不等于用户已经升级。安装的应用不会自动获取提交；用户需要正式发布的安装包或自行构建。请将“本地测试通过”“远端 CI 通过”“Release 已公开”“真实硬件验收”分别记录。

## 维护者：正式发布

1. 在准备发布的提交上核对 `Resources/Info.plist` 的版本及构建号、界面版本、CHANGELOG 和相关说明。
2. 完成本地测试、构建及严格验签。风扇协议或恢复逻辑变化时，单独做有人观察的实机验收；普通 CI 不替代它。
3. 检查 GitHub 上目标提交的检查结果，确认提交、标签版本与发布说明一致。
4. 由维护者明确决定创建并推送版本标签，例如：

   ```sh
   git tag -a v0.5.0 -m "StateLite 0.5.0"
   git push origin v0.5.0
   ```

   示例是发布动作，不要在尚未准备好时照抄执行；不要覆盖或强推已发布标签。
5. 标签工作流构建并创建 **draft release**，资产包括：
   - `StateLite-vVERSION-macos-arm64.zip`
   - `SHA256SUMS`
   - `release-metadata.json`
6. 从草稿下载资产，核对哈希、版本和元数据中的来源提交，解压后严格验签，并做必要的本机打开验证。检查发布说明准确保留尚未验证项目。
7. 维护者确认无误后手动 **Publish release**。草稿存在、工作流成功或附件上传完成都不等于已经发布。
8. 发布后核对公开页面与资产，再从应用手动“检查更新”验证提示。只有此时才能报告公开更新可用。

CI 文件是自动化行为的最终依据；查看仓库 `.github/workflows/`。本文描述发布流程，不声称任何远端工作流或 Release 已经运行成功。每个版本的发布状态以 [Actions](https://github.com/ARMANDSnow/StateLite/actions) 和 [Releases](https://github.com/ARMANDSnow/StateLite/releases) 为准。

## 回退

先切回系统控制并退出，再用可信旧包替换完整应用。旧构建代码身份可能与当前安装助手不一致，因此回退后的首次调速也可能需要授权更新。不要为避免授权而手动改写助手 manifest 或删除恢复标记。
